# Blocker handling

Use these statuses honestly:

- `PASS`
- `FAIL`
- `MACHINE-VERIFIED`
- `MANUAL-PASS`
- `MANUAL-UNVERIFIED`
- `BLOCKED-EXTERNAL`
- `WAIVED` only with explicit Kevin authorization
- `NOT ATTEMPTED`

Do not use `BLOCKED` as a shortcut for difficult code.

When a blocker appears:

1. preserve the failing evidence;
2. identify the narrow blocked edge;
3. roll back or isolate unsafe partial behavior;
4. finish all safe local implementation and fixtures;
5. write exact manual verification or missing-credential steps;
6. mark only that edge `BLOCKED-EXTERNAL`;
7. continue every independent task.

Examples of genuine external/manual gates:

- a real device is required;
- a live provider account or OAuth consent is required;
- deployment authorization is required;
- a secret would be required;
- elapsed real-world adoption time is required.

A product choice, naming choice, layout choice, implementation choice, failing test, or long diff is not a genuine external blocker.
